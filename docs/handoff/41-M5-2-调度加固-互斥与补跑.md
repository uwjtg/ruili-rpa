## 1. 本阶段目标与完成情况

handoff 40 §5 列的调度两个尾巴一次收掉：

1. **运行中互斥**：RunManager 加 `isRunning()`（跑置 interpreter=null，空闲返 false）；TaskScheduler ctx 加 `isRunning()` 回调。到点时若已有流程在跑，本次**跳过**（不覆盖 interpreter、不打断上一次），只调新 DB 函数 `markTaskTick(id, next)` 推进 next_run_at，**不增 run_count、不动 last_run_at**；
2. **错过补跑**：`reload(tasks, opts?)` 加 `catchUp` 与 `graceMs`（默认 5 分钟）。仅启动时 `whenReady` 传 `{catchUp:true}`——对每个启用任务，若 DB 存的 `next_run_at` 已在过去且未超过 grace（关机/睡眠期间错过），用 `queueMicrotask` 立即补跑一次；超过 grace 或 next_run_at 为 null（从未跑）则不补跑。启停/增删后的 reload 不传 catchUp，不会误补跑。

## 5. 遗留问题

1. **补跑只补一次**：关机超过 grace（5 分钟）的连续多个错过点不补跑，直接对齐下一次（防止开机雪崩）；如需"补跑最近 N 次"后续再加；
2. **互斥粒度是全局**：不同任务之间也互斥（同一时刻只跑一个流程）；RunManager 本就是单例，这是对的；未来若支持并行跑多流程需重设计；
3. **补跑后 next_run_at 对齐**：补跑那一次仍走 run() 末尾的 nextAt()，cron 取下一个未来时刻、interval 取 now+intervalMs，不会立刻再补跑；
4. **RobotsView 执行记录视图仍未做**（读 logs 表）；热键/文件监听触发器未做；
5. 进程被 kill -9 时 markTaskTick/markRan 未落盘的 next_run_at 会丢，下次启动按旧值判断是否补跑（在 grace 内会补一次，可接受）。
