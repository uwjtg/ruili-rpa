§0

摘要：结论先行

Executive Summary
  • 可行性 — 影刀核心能力域全部有成熟开源组件复用；自研薄层仅三块：AST 解释器（约 2-3 千行）、指令插件框架、V3 UI 真实数据化。
  • 一致性策略 — 以「高频场景 80% 覆盖、单条指令体验一致」为 V1 目标，而非指令总数一致（影刀 800+ 条为多年积累）。
  • 最大风险 — ① 元素选择器稳定性（影刀核心壁垒）；② 开源许可证合规（M0 强制审计）；③ 桌面自动化兼容性（WPS / 老软件 / UAC / DPI）。
  • 建议路线 — Electron 壳（沿用 V3 设计）+ Node 执行引擎 + Playwright（网页）+ Python sidecar（图像 / OCR / 复杂桌面）+ SQLite（本地存储）。

4.2为什么不整体二开现成开源 RPA

  • OpenRPA（MPL-2.0）— 功能全，但基于 Windows Workflow Foundation + .NET 老栈，设计器交互与 V3 原型差异大；MPL 文件级开源义务会污染核心代码；指令体系面向欧美场景。仅作参考读物。
  • taskt（MIT）— .NET Framework 老栈、社区活跃度低，只适合当参考。
  • n8n / Node-RED— 编排引擎优秀，但 n8n 是 Sustainable Use License（不可直接商用改造）；Node-RED 节点模型面向服务端集成而非 RPA 元素操作。

结论：「V3 原型 + 自研薄引擎 + 开源能力库」的组合，比「二开某开源 RPA 再改 UI」总成本更低、可控性更强。

§5

总体架构

Architecture

5.1流程 DSL（JSON AST）

按交接文档 §6 建议，修正原型的 indent 展平表达，改为树形结构；执行前校验块闭合、空分支、变量未定义警告、循环深度上限。

{
  "version": 1,
  "name": "商品比价",
  "vars": [{ "name": "priceList", "type": "list", "value": [] }],
  "steps": [
    { "id": "s1", "cmdId": "openUrl", "params": { "url": "https://…" } },
    { "id": "s2", "cmdId": "loop", "params": { "listVar": "priceList", "itemVar": "item" },
      "children": [
        { "id": "s2-1", "cmdId": "if", "params": { }, "children": [ ], "else": [ ] }
      ] }
  ]
}

5.2指令插件 schema（UI 与引擎共用，演进自原型 CMDS）

interface CmdSchema {
  id: string;  name: string;  group: string;  icon: string;
  params: ParamField[];               // k / l / t / v / opts + 校验规则
  summary: (p) => string;             // 步骤摘要（原型已实现，沿用）
  hasEnd?: boolean;                   // 循环 / 分支块尾标记
  runner: async (ctx, p) => any;      // ctx: 变量表 / 日志 / 取消令牌 / 进度
}

指令库即插件注册表：新增指令 = 注册一个 schema，UI（左侧库、参数面板、摘要）与引擎（runner）自动获得该指令。自定义指令暴露「执行 Python 片段」「执行 JS 片段」两个兜底节点 + .json 流程包导入导出。

Gap Analysis

以下 10 项是与影刀存在客观差距的地方。每项说明原因、给出解决方案与用户感知差异——这是本计划书的核心章节。

表 6-1 · 差距清单与对策
#影刀的功能为什么做不到完全一致解决方案用户感知差异
6.1800+ 条指令总量多年积累，一次性对齐不现实指令插件框架让扩指令成本极低；V1 做 150-180 条高频指令；提供「执行 Python / JS 片段」兜底节点；.json 流程包导入导出少数低频场景用脚本节点替代；高频场景无感
6.2元素选择器稳定性（动态页面自愈、疑难控件）核心壁垒，含大量长尾兼容性修补，无法短期复制三层策略：① Playwright auto-waiting 起步；② 选择器回退链（id→name→aria→css→xpath→可见文本→相对位置锚点），录制时冗余存特征，回放失败按链重试；③ 桌面疑难控件保留图像 / 坐标兜底。「选择器自愈」列为长期迭代项（双周按失败案例补特征）简单页面无感；复杂页面初期失败率高于影刀，随迭代收敛
6.3魔法指令（NL→流程）效果影刀内置模型经私有调优与流程语料训练接 OpenAI 兼容大模型（智谱 / DeepSeek 等可配）：function-calling 传入指令 schema，生成 JSON AST → 编辑器确认后运行；AI 面板兼做报错解释与流程问答生成成功率取决于模型与场景；生成的流程「可查看可修改」，比黑盒更透明
6.4智能录制 / 数据抓取向导成熟度相似元素识别与去噪经多年打磨V1：浏览器内操作录制（CDP 事件→指令序列）+ 抓取向导（DOM 兄弟节点聚类→相似元素列表→字段标注）；桌面录制降级为「键鼠录制 + 手动拾取」桌面录制体验弱于影刀；浏览器抓取可达到可用水平
6.5企业控制台（云端集群、权限、审计）影刀企业版是 SaaS 服务，非客户端功能V1 明确不做，用「流程包导出 + 共享目录」过渡；V2 自建轻量 Web 控制台（React + NestJS + PostgreSQL + WebSocket 心跳 / 下发）企业集中管控场景 V1 缺失；单机 / 小团队无感
6.6模板市场 / 指令市场生态需云端后端 + 社区运营内置官方模板 30-50 个随包分发；.json 流程包一键导入导出；社区市场随 V2 控制台上线模板数量少于影刀；不阻塞使用
6.7验证码 / 滑块等对抗场景影刀部分对接第三方打码平台；对抗性场景有合规风险接打码平台 API 的适配指令（用户自备账号）；对外声明仅模拟人工操作、不绕过技术保护措施；滑块轨迹模拟可做，成功率不承诺此类场景成功率天然波动，影刀亦然
6.8Android 手机自动化（群控）影刀手机端是独立产品线V3 远期：adb + uiautomator2（MIT）+ scrcpy（Apache-2.0），技术可行，排期在 PC 端成熟后V1 / V2 无手机端
6.9Office / WPS 深度兼容（公式重算、宏）依赖真实 Office / WPS 进程行为的长期测试积累双轨策略：后台批处理用 exceljs；需公式重算 / 透视表 / 宏的场景走 COM 驱动真实 Office / WPS；建立 WPS + Office 双环境回归用例集边缘 Excel 特性（宏、加载项）以 COM 模式覆盖
6.10品牌迁移成本（影刀用户迁来）指令命名、快捷键习惯不同① 指令命名对齐影刀常用习惯（不抄文案）；② 提供迁移说明文档；③ 教程视图内置上手课程需半天上手时间

§8

Dev Model

本项目不设人类编码团队，全部编码由 AI 编码智能体完成；人类角色是产品决策、验收测试与集成把关。

§10

法律合规红线

Compliance
  • 不反编译、不逆向影刀客户端。只做黑盒行为对标（界面范式、功能集）；V3 交接文档已确认视觉与代码全部自有，继续保持。
  • 不使用影刀商标、logo、文案、截图作任何宣传素材。
  • 开源许可证义务：全部组件履行声明义务（附 THIRD-PARTY-NOTICES）；AGPL / GPL 组件不进主程序（仅作为用户机器上独立进程被调用的工具，需法务确认后放行）。
  • 数据安全：用户凭据与敏感变量用 DPAPI 加密存储，日志默认脱敏。
  • 产品内嵌《合规使用声明》：模拟人工操作、不绕过技术保护措施，用户对目标网站条款自负其责。
