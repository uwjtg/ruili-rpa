## 0. 摘要（结论先行）

1. **可行性**：影刀的核心能力域（网页自动化、桌面自动化、Excel、流程编排、调度触发）全部有成熟开源组件可复用，真正需要从零写的只有三块薄层：流程 AST 解释器（约 2-3 千行）、指令插件框架、以及 V3 UI 的真实数据化改造。这三块都是常规工程，无技术黑箱。
2. **一致性策略**：以"高频场景 80% 覆盖、单条指令体验一致"为 V1 目标，而不是指令总数一致（影刀 800+ 条指令是多年积累，一次性对齐不现实）。§3 给出逐模块一致度目标。
3. **最大风险**（按严重度）：
   - 元素选择器稳定性（影刀多年打磨的核心壁垒，需要长期投入）
   - 开源许可证合规（有传染性许可的雷区，M0 强制审计）
   - 桌面自动化兼容性（WPS/老软件/UAC/DPI）
4. **建议技术路线**：Electron 壳（沿用 V3 原型设计）+ Node 执行引擎 + Playwright（网页）+ Python sidecar（图像/OCR/复杂桌面）+ SQLite（本地存储）。备选路线对比见 §4.3。

## 1. 目标与范围

**目标**：开发一款 Windows 桌面端 RPA 客户端，功能对标影刀 RPA；UI 按 V3 设计定稿实现；优先复用开源组件。

**V1 范围内**：
- 7 视图客户端（首页工作台 / 应用 / 流程编辑器 / 触发器·计划任务 / 机器人 / 市场 / 教程）
- 可视化流程编辑器（真实数据化：AST、参数面板、变量、元素库、断点调试、撤销重做）
- 指令执行引擎 + 指令库 150+ 条（覆盖 9 大分类）
- 元素拾取器（浏览器 + 桌面）、智能录制（浏览器优先）、数据抓取向导 V1
- 计划任务（cron/间隔）、热键触发、文件监听触发
- 本机机器人（托盘/静默运行、执行记录、日志落盘）
- AI 助手（LLM 生成流程、报错解释）+ AI 类指令（大模型对话/OCR/文档提取）
- 本地持久化（SQLite）、安装包与自动更新

**V1 范围外**（进 V2/V3，见 §7 里程碑备注）：企业云端控制台、Android 自动化、macOS、云端模板市场后端、团队协作/权限。

## 2. 现状盘点：V3 交接包给了什么、缺什么

| 层 | 现状 | 评价 |
|---|---|---|
| 设计系统 | CSS token 全套（色彩/字体/密度/组件规格） | 可直接迁移为代码 Design Token |
| 7 视图 UI | 高保真可交互原型，交互全部可点 | 需 React/Vue 组件化 + 接真实数据 |
| 流程编辑器 | 添加指令/参数编辑/变量高亮/断点/禁用/复制/拖拽排序/撤销重做/多标签页/日志，全部已实现（前端模拟） | 交互规格 = 验收口径，只需把"模拟"换成"真实" |

| 拾取/录制/抓取 | 占位按钮 | 本计划书的主要工作量 |

## 3. 对标基线：影刀功能全景与一致度目标

影刀 RPA 客户端的能力面拆解为 12 个模块，逐一定锐流 V1 的一致度目标（"一致"指：同类操作在锐流中有同等体验的对应物，不要求逐字逐参数相同）：

| 模块 | 影刀现状 | 锐流 V1 方案 | 一致度目标 |
|---|---|---|---|
| 指令库 | 约 800-1000 条指令、20+ 分类 | 150-180 条覆盖高频 80% 场景，支持自定义指令/脚本节点兜底 | 指令数不一致；单条体验一致 |
| 网页自动化 | Chrome/Edge 元素级自动化、数据抓取向导、浏览器管理 | Playwright（CDP 连接真实浏览器）+ 自研抓取向导 | 90% |
| 桌面软件自动化 | UIA/MSAA 元素级 + 键鼠模拟 | Python sidecar（pywinauto/uiautomation）+ nut-js 键鼠 | 80% |
| Excel/表格 | 全套读写、公式、透视表、WPS 兼容 | exceljs 读写 + COM 模式（驱动真实 Office/WPS）双轨 | 85% |
| 图像/OCR | 找图点击、OCR 文字识别、验证码 | OpenCV 模板匹配 + RapidOCR；验证码见 §6.7 | 85%（验证码除外） |
| 流程编辑器 | 拖拽、调试、变量、元素库、录制 | 按 V3 原型全量真实化 | 90% |
| 调试 | 断点、单步、变量监视、日志 | 同（原型交互已定稿，引擎侧实现） | 95% |
| 魔法指令（AI 生成流程） | 自然语言→流程，内嵌大模型 | LLM function-calling 生成 AST | 70%（依赖模型，见 §6.3） |
| 调度/触发器 | 定时、热键、文件/邮件监听、错过补跑 | croner + uiohook + chokidar + 补跑队列 | 90% |
| 机器人 | 本机运行器、托盘、静默、执行记录 | 同（与设计器共用引擎，无头模式） | 90% |
| 企业控制台 | 云端机器人集群、权限、审计 | V1 不做；V2 自建 Web 控制台 | 0%（明确差距，§6.5） |
| 市场/学院 | 模板市场、指令市场、教程 | 内置官方模板 30+、本地导入导出（.json 流程包） | 部分一致（§6.6） |

### 4.2 为什么不整体二开现成开源 RPA（OpenRPA / taskt）

- **OpenRPA**（MPL-2.0）：功能全，但基于 Windows Workflow Foundation + .NET 技术栈，设计器交互与 V3 原型差异大，UI 重做成本 ≈ 重写；MPL 文件级开源义务会污染核心代码；其指令体系面向欧美场景。
- **taskt**（MIT）：.NET Framework 老栈、社区活跃度低，只适合当参考读物。
- **n8n / Node-RED**：编排引擎优秀，但 n8n 是 Sustainable Use License（不可直接商用改造）、Node-RED 的节点模型面向服务端集成而非 RPA 元素操作。
- **结论**：V3 原型 + 自研薄引擎 + 开源能力库的组合，比"二开某开源 RPA 再改 UI"总成本更低、可控性更强。OpenRPA 的源码作为"指令如何落地"的参考库。

### 4.3 路线对比（决策用）

| 路线 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| A. Electron + Node 引擎 + Python sidecar（推荐） | 自动化生态最全；UI 迁移最快；sidecar 隔离 Python 依赖 | 安装包约 +40MB；双进程通信 | **推荐** |
| B. Electron + .NET sidecar（FlaUI, Apache-2.0） | 桌面自动化更强、单语言后端 | 图像/OCR 生态弱于 Python；两套 sidecar 或弃用 Python 库 | 备选 |
| C. Tauri + Rust | 包最小 | 自动化库生态薄，Playwright/pywinauto 均无法直接用，工期 +30% | 不推荐 V1 |

### 4.4 许可证红线（M0 强制审计）

| 禁用/慎用 | 原因 | 替代 |
|---|---|---|
| EPPlus 5+ | Polyform Noncommercial（禁商用） | exceljs / NPOI（Apache-2.0） |
| PyMuPDF | AGPL（传染） | pdfium / pdf-lib |
| Emgu.CV | GPL + 商业双授权 | opencv-python（sidecar 进程隔离） |
| n8n 源码 | Sustainable Use License | 只做架构参考，不抄代码 |
| AutoIt | 免费但非开源，分发受限 | 不引入；键鼠用 nut-js/SendInput |

## 5. 总体架构

### 5.1 进程模型

```
┌─ 锐流客户端（Electron）──────────────────────────────┐
│  Renderer（React + V3 设计 token）                     │
│   7 视图 · 编辑器 · 参数面板 · 日志面板                │
│        │ IPC（指令目录/流程JSON/日志流/运行控制）        │
│  Main（窗口/托盘/调度/触发）                            │
│   croner 定时 · uiohook 热键 · chokidar 文件监听        │
│        │ Node Worker（引擎进程，可被机器人模式独立拉起） │
│   AST 解释器 → 指令注册表 → 各能力域执行器              │
│     ├ web: Playwright(CDP→真实 Chrome/Edge)            │
│     ├ office: exceljs / docx / pdf-lib / COM(Excel|WPS)│
│     ├ desktop: nut-js 键鼠 + sidecar(UIA 窗口/控件)    │
│     └ ai: LLM 适配层 / 消息通知 webhook                │
│  Python Sidecar（随安装包发布，HTTP/stdio 通信）        │
│   opencv-python 找图 · RapidOCR · pywinauto UIA        │
└──────────────────────────────────────────────────────┘
   本地存储：SQLite（应用/流程/任务/日志/元素库）
             + safeStorage 加密凭据
```

- **设计器与机器人分离**：同一引擎两种形态——设计器进程带 UI；机器人模式（托盘/静默/计划唤醒）无头拉起引擎 worker，执行同一份流程 JSON。这与影刀"开发/运行"分离的范式一致。
- **日志链路**：引擎 worker 逐步骤推流（步骤开始/结束/日志四级/变量快照）→ IPC → 日志面板 + 落盘 SQLite（脱敏存储）。

### 5.2 流程 DSL（JSON AST）

按交接文档 §6 的建议，修正原型的 indent 展平表达，改为树形：

```json
{
  "version": 1,
  "name": "商品比价",
  "vars": [{"name":"priceList","type":"list","value":[]}],
  "steps": [
    {"id":"s1","cmdId":"openUrl","params":{"url":"https://..."}},
    {"id":"s2","cmdId":"loop","params":{"listVar":"priceList","itemVar":"item"},
     "children":[
       {"id":"s2-1","cmdId":"if","params":{},"children":[],"else":[]}
     ]}
  ]
}
```

执行前校验：块闭合、空分支、变量未定义警告、循环深度上限。

### 5.3 指令插件 schema（UI 与引擎共用，演进自原型 CMDS）

```ts
interface CmdSchema {
  id: string; name: string; group: string; icon: string;
  params: ParamField[];            // k/l/t/v/opts + 校验规则
  summary: (p) => string;          // 步骤摘要（原型已实现，沿用）
  hasEnd?: boolean;                // 循环/分支块尾标记
  runner: async (ctx, p) => any;   // ctx: 变量表/日志/取消令牌/进度
  category: { color?: string };
}
```

- 指令库即插件注册表：新增指令 = 注册一个 schema，UI（左侧库、参数面板、摘要）与引擎（runner）自动获得该指令。
- 自定义指令：暴露"执行 Python/JS 片段"两个兜底节点 + 流程包导入导出（.json）。

## 6. 无法与影刀完全一致的功能及解决方案（核心章节）

| # | 影刀的功能 | 为什么做不到完全一致 | 解决方案 | 用户感知差异 |
|---|---|---|---|---|
| 6.1 | 800+ 条指令总量 | 是多年积累，一次性对齐不现实 | 指令插件框架让扩指令成本极低；V1 做 150-180 条高频指令；提供「执行 Python 片段」「执行 JS 片段」兜底节点；支持 .json 流程包/自定义指令导入导出 | 少数低频场景需用脚本节点替代；高频场景无感 |
| 6.2 | 元素选择器的稳定性（动态页面自愈、疑难控件） | 核心壁垒，含大量长尾兼容性修补，无法短期复制 | 三层策略：① Playwright auto-waiting 起步；② 选择器回退链（id→name→aria→css→xpath→可见文本→相对位置锚点），录制时冗余存特征，回放失败按链重试；③ 桌面疑难控件保留图像/坐标兜底指令。把"选择器自愈"列为长期迭代项（每双周按失败案例补特征） | 简单页面无感；复杂页面初期失败率高于影刀，随迭代收敛 |
| 6.3 | 魔法指令（NL→流程）的效果 | 影刀内置模型经过私有调优与流程语料训练 | 接 OpenAI 兼容大模型（智谱/DeepSeek/…可配）：function-calling 传入指令 schema 作为 tools，生成 JSON AST → 进入编辑器确认后运行；AI 面板同时做报错解释、流程问答 | 生成成功率取决于模型与场景；生成的流程总是"可查看可修改"（比黑盒更透明） |
| 6.4 | 智能录制 / 数据抓取向导成熟度 | 影刀的相似元素识别与去噪经过多年打磨 | V1：浏览器内操作录制（CDP 事件→指令序列）+ 数据抓取向导（DOM 兄弟节点聚类→相似元素列表→字段标注）；桌面录制降级为"键鼠录制 + 手动拾取" | 桌面录制体验弱于影刀；浏览器抓取可达到可用水平 |

| 6.6 | 模板市场/指令市场生态 | 需要云端后端 + 社区运营 | 内置官方模板 30-50 个（随包分发）；.json 流程包一键导入导出；社区市场随 V2 控制台上线 | 模板数量少于影刀；不阻塞使用 |
| 6.7 | 验证码/滑块等对抗场景 | 影刀部分对接第三方打码平台；对抗性场景有合规风险 | 接打码平台 API 的适配指令（用户自备账号）；对外声明仅模拟人工操作、不绕过技术保护措施；滑块轨迹模拟可做，成功率不承诺 | 此类场景成功率天然波动，影刀亦然 |

## 8. 开发模式：AI 智能体开发（V1.1 修订）

本项目不设人类编码团队，全部编码由 AI 编码智能体完成；人类角色是产品决策、验收测试与集成把关。

| 角色 | 承担方 | 职责 |
|---|---|---|
| 编码实现 | AI 编码智能体（多会话并行） | 按任务包实现代码 + 单元测试 + 自检报告 |
| 产品/架构决策 | 用户 | 拍板决策点、评审设计文档、控制范围 |
| 验收测试 | 智能体 + 用户 | 智能体跑自动化用例（vitest/pytest）；用户做端到端冒烟（真实浏览器/Office/WPS/记事本） |
| 设计 | 已定稿（V3 原型） | 图标按 V3 规范由智能体自绘 SVG 补齐 |
| LLM 调用 | 配置化 Provider（决策⑤） | 按任务选模型：魔法指令用强模型，报错解释/摘要用便宜模型 |

**任务包规范**（下发编码会话时遵循）：每个任务包含【目标 / 输入 / 产出物 / 技术要点 / 验收标准 / 注意事项】，智能体完成时必须输出「变更文件清单 + 测试运行结果原文 + 自检清单 + 遗留问题」；一个任务包一个 git 分支，验收通过后合入 main。任务拆解与派单模板见《锐流RPA-V3-M0-任务拆解.md》。

## 10. 法律合规红线

1. **不反编译、不逆向影刀客户端**；只做黑盒行为对标（界面范式、功能集），V3 交接文档已确认视觉与代码全部自有，继续保持。

4. 用户凭据/变量中的敏感值用 DPAPI 加密存储，日志默认脱敏。
5. 产品内嵌《合规使用声明》：模拟人工操作、不绕过技术保护措施、用户对目标网站条款自负其责。
