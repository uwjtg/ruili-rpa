# 锐流 RPA V3 · 接力开发模式说明

> 版本 V1.0 · 2026-09-24 · 上游文档：《锐流RPA-V3-开发计划书.md》（V1.1）+《锐流RPA-开发交接文档.md》（V3）+ 原型 HTML ×2
> 用途：**每个阶段对话的必读文件**。本文件定义「阶段接力 + 交接文档 + 末尾核对」的开发模式，替代原《锐流RPA-V3-M0-任务拆解.md》的「任务包派单 + 人工逐包验收」。

---

## 0. 为什么用接力模式

原 M0 任务拆解把工作切成 11 个任务包（T0-T10）、要求多会话并行、每包独立分支、用户逐包验收——对单人 + AI 智能体开发来说维护成本过高。本模式改为：

- **串行阶段接力**：6 个阶段依次执行，一次只碰一块代码，一个 `main` 分支滚动；
- **交接文档即事实源**：每个阶段自动生成交接文档落盘 `docs/handoff/`，下一阶段对话直接读文件接手，无需复制粘贴；
- **末尾一次核对**：阶段 6 汇集全部交接文档与代码做交叉核对，输出《M0 收尾核对报告》；
- **最少人工**：全流程仅 3 个人工介入点（§6），决策默认按推荐执行并留痕。

---

## 1. 核心原则

1. **唯一事实源**：计划书 V1.1 管「做什么 / 用什么 / 什么顺序」，交接文档管「界面长什么样 / 交互怎么验收」，本文件管「阶段怎么接力」；每阶段的交接文档是下一阶段的唯一输入。
2. **串行接力**：不做并行任务包、不做多分支；需要并行的场景（如阶段 3 的网页/Excel 与 sidecar）按目录拆分、各出各的交接文档，由阶段 6 统一合并核对。
3. **最少人工**：3 个 ★ 介入点（§6），其余全部由对话自动完成（编码、测试、自检、交接文档、核对）。
4. **决策默认推荐**：需要拍板的点默认按推荐执行，并记录在交接文档第 7 段；用户可随时推翻，推翻后由当前阶段对话或下一阶段对话落实。

## 2. 阶段划分

| 阶段 | 范围（映射原任务包） | 验收标准 | 产出 |
|---|---|---|---|
| 阶段 1 · 骨架与壳 | T0 + T1 | `npm i && npm test && npm run dev` 三连绿；7 视图可导航切换；控制台无报错 | 仓库、设计 token、壳组件、交接 01 |
| 阶段 2 · 引擎核心 | T2 + T3 + 断点 | vitest ≥ 10 例全绿；5 步演示流程跑通；断点暂停/继续可用 | AST 解释器、指令注册表、8 条演示指令、交接 02 |
| 阶段 3 · 真实链路 | T4 + T5 + T6 | `poc:web` / Excel round-trip / `poc:sidecar` 三个 POC 全跑通 | 网页 CDP、Excel 读写、Python sidecar、交接 03 |
| 阶段 4 · 贯通与 AI | T7 + T8 | 日志面板接真实事件流；双 Provider 切换成功；function-calling 生成合法流程 AST | 日志流 IPC、LLM 配置化、交接 04 |
| 阶段 5 · 审计与设计 | T9 + T10 | `license-check` 0 违规；选择器回退链设计稿评审通过 | 许可证审计、NOTICES 草稿、selector 设计稿、交接 05 |
| 阶段 6 · 收尾核对 | 新增（汇集核对） | M0 出口演示真实跑通；核对报告无未闭环遗留（或显式挂账） | 《M0 收尾核对报告》、计划书 §9 风险册与排期更新 |

接力流程：

```
阶段1 →(交接01)→ 阶段2 →(交接02)→ 阶段3 →(交接03)→ 阶段4 →(交接04)→ 阶段5 →(交接05)→ 阶段6 → M0 出口
```

## 3. 每阶段执行协议（阶段对话必做）

1. **开工前必读**：本文件 + 计划书 V1.1 + 交接文档（原型 HTML 随 T0 入库到 `docs/`）+ 上一阶段交接文档（`docs/handoff/NN-*.md`）。
2. **只动本阶段目录**（阶段 1 建目录见下）；改动公共文件（`package.json`、`tsconfig.json`、根配置）必须在交接文档中显式声明 diff。
3. **阶段内自验**：以自动化测试为准（vitest / pytest），§2 验收标准全部达成才算完成，不依赖人工逐包验收。
4. **完成时生成交接文档**：按 §4 模板，落盘 `docs/handoff/NN-*.md`，并更新 `docs/handoff/INDEX.md`（阶段 1 创建该索引）。
5. **输出「下一阶段输入要求」**：要接的接口签名、约定、注意事项，写进交接文档第 6 段。

仓库目录（阶段 1 按此创建，与交接文档 §8 对齐并扩展）：

```
ruili-rpa/
  src/renderer/   # React UI（7 视图）
  src/main/       # Electron 主进程：窗口、调度、IPC、sidecar 桥
  src/engine/     # 引擎：core / commands / web / excel / llm
  src/shared/     # 指令 schema、AST 类型、事件类型（UI 与引擎共用）
  sidecar/        # Python sidecar（阶段 3 填充）
  docs/           # 计划书 V1.1、交接文档、原型 html×2、handoff/
  tests/          # 跨模块端到端用例（阶段 6 前填充）
```

## 4. 交接文档模板（7 段）

每个阶段对话完成时必须按以下结构生成交接文档：

```markdown
# 阶段 N 交接文档（日期）

## 1. 本阶段目标与完成情况
（目标、实际完成内容、未完成内容）

## 2. 产出物清单
（文件路径 + 关键接口签名，如：`src/engine/core/interpreter.ts` 导出 `run(flow, ctx)`）

## 3. 测试结果原文
（npm test / pytest 运行结果摘要，注明用例数与绿/红）

## 4. 自检清单
（对照 §5 统一 DoD，逐条打勾）

## 5. 遗留问题
（含影响与建议，不隐瞒）

## 6. 对下一阶段的输入要求
（要接的接口、约定、注意事项，如：事件类型已定义于 src/shared/events.ts，请按此订阅）

## 7. 待用户拍板的决策
（附推荐项；默认按推荐执行，用户可推翻）
```

## 5. 统一 DoD（每个阶段必须满足）

- [ ] 产出物落盘约定路径
- [ ] `npm test`（引擎/renderer）与 `pytest`（sidecar）全绿，并附运行结果原文
- [ ] 新增功能代码带单元测试（引擎核心路径必测；UI 允许手动冒烟）
- [ ] 未引入禁用依赖：EPPlus 5+ / PyMuPDF / Emgu.CV / n8n 源码 / GPL·AGPL 进主程序
- [ ] 无硬编码密钥、令牌；示例数据不含真实凭据
- [ ] 未反编译、未引用影刀任何二进制或资源文件
- [ ] 交接文档 7 段写满并落盘 `docs/handoff/`

---

## 6. 人工介入点（全流程仅 3 次）

| # | 时机 | 动作 | 前置条件 |
|---|---|---|---|
| ★1 | 现在 | 拍板本模式 + 计划书 §11 六项决策；确认阶段 1 开始 | 本文件已就绪 |
| ★2 | 每个阶段结束 | 开一个新对话，粘贴 §8 开场白模板（含上一阶段交接文档路径） | 该阶段交接文档已落盘 |
| ★3 | 阶段 6 之后 | 读《M0 收尾核对报告》，做一次端到端冒烟验收（真实浏览器 / Office / WPS / 记事本） | 核对报告已交付 |

除此之外不需要人工介入。外部凭据（LLM key、打码平台账号等）需在用到前由用户备好，配置入口已在计划书决策⑤ / 阶段 4 定义。

---

## 7. 阶段 6 收尾核对清单

收尾对话汇集 `docs/handoff/01-05` 全部交接文档与代码，逐项核对并输出报告：

1. **接口契约对齐**：`src/shared` 的指令 schema / AST 类型 / 事件类型在引擎、主进程、渲染端三处使用一致（以交接文档第 2/6 段为准）。
2. **验收标准逐条核对**：每个阶段的验收标准（§2）是否达成，以交接文档第 3 段测试原文为证据。
3. **公共文件改动声明齐全**：`package.json` / `tsconfig.json` 等改动均有声明，无静默修改。
4. **遗留问题闭环或挂账**：每阶段第 5 段遗留问题要么已解决，要么显式挂账（注明影响与负责阶段）。
5. **决策汇总**：全部「待拍板」项都有最终结果（默认推荐或已被推翻），汇总成决策记录。
6. **禁用依赖扫描**：重跑 `license-check`，0 违规。
7. **M0 出口演示**：在开发壳内运行一条真实流程——打开 Edge → 输入搜索词 → 点击搜索 → 提取第一条结果标题 → HTTP GET → 写入 Excel → 全屏截图 → OCR 出文字 → 汇总 log，全程日志流式显示，中途断点暂停一次后继续。
8. **计划书更新**：回写 §9 风险登记册与实际工期；产出 M1 阶段拆解建议。

## 9. 已消化的评审问题（2026-09-24 评审 → 本模式的处理）

| 原评审问题 | 本模式的处理 |
|---|---|
| B1 计划书 HTML 版本混装（V1.0/V1.1） | 以 MD V1.1 为唯一事实源；HTML 仅作阅读版，不再作为修订载体 |
| B2 T3 × T7 文件所有权冲突（src/shared） | 串行接力天然消除；公共文件改动改为「交接文档显式声明」 |
| B3 M0 出口要求断点但无任务包实现 | 断点 / 暂停-继续并入阶段 2（引擎核心 POC） |
| B4 浏览器连接方案矛盾（独立 profile vs「对用户无感」） | 阶段 3 统一为「独立 profile 启动 + 明示用户感知差异（目标站需重新登录）」；「附加日常浏览器」列为远期探索 |
| B5 串行链分支策略未定义 | 单 `main` 滚动，无多分支；阶段 6 统一核对 |
| I1 M3 验收口径不可判定 | 阶段 5 选择器设计稿 + 阶段 6 出口演示时落地：站点清单、成功率口径、失败上报格式 |
| I4 LLM function-calling 全量 tools 超限 | 阶段 4 按「指令子集（按场景/关键词挑选）」方式做 POC |
| I5 DoD「引擎逻辑 100% 有测试」不可度量 | 改为「核心执行路径 100% + 整体 ≥ 90%（vitest coverage 口径）」 |
| I7 AI 效率假设未验证 | 阶段 6 用实际工期校准 M1+ 排期，并在计划书 §9 登记「AI 开发效率不达标 / 集成摩擦」风险 |

其余 S 级细节（技术栈版本锁定、国内网络镜像、sidecar 协议统一、更新源、杀软白名单等）已写入对应阶段的「技术要点」随派单执行。
